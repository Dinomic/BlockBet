# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

Monorepo with several independent parts (no root build file):

- `Backend/` — Spring Boot (Java 25, Maven) REST API that manages accounts, custodial Ethereum wallets and token transfers.
- `Mobile/` — Flutter app (`bbmobile`) that consumes the backend.
- `Blockchain/` — private Ethereum (geth v1.13.8) network via `docker-compose.yml` (bootnode + nodes + netstats dashboard), `genesis.json`, chain ID `12345`. Node data dirs (`node1..3`, `secrets`) are git-ignored. Reset: `docker compose down -v`, delete `node1 node2 node3`, `docker compose up` (on Windows, the notes recommend WSL Ubuntu-24.04).
- `Terraform/`, `Bruno/` — infra and API request collections (Bruno is git-ignored).

## Commands

Backend (run from `Backend/`):

```powershell
./mvnw spring-boot:run          # run API (needs Postgres + the blockchain node, see below)
./mvnw clean package            # build; also regenerates OpenAPI sources
./mvnw test                     # all tests
./mvnw test -Dtest=ClassName#method   # single test
```

Mobile (run from `Mobile/`):

```powershell
flutter pub get
flutter run --dart-define=API_BASE_URL=http://<host>:8080   # default is http://10.0.2.2:8080 (Android emulator → host)
flutter test
flutter test test/path_test.dart
flutter analyze
```

## Backend architecture

Package root `com.dinomic.blockbet`: `controllers` → `services` (interface `I*Service` + `services/impl`) → `repositories` (`I*Repo`, Spring Data JPA) → `daos` (JPA entities). MapStruct mappers live in `mappers`.

- **Contract-first API**: controllers implement interfaces generated by `openapi-generator-maven-plugin` from `src/main/resources/apis/authenticationApi.yaml`, `blockbetApi.yaml` (`GeneralController`), `bookieApi.yaml` (`BookieController`), `bettorApi.yaml` (`BettorController`) and `internalApi.yaml` (`InternalController`); the last three reference shared schemas in `blockbetApi.yaml` (packages `blockbet.openapi.api` / `blockbet.openapi.model`, generated at build time into `target/`). To change an endpoint or DTO, edit the YAML and rebuild; don't hand-write the models. Config uses `openApiNullable=false` and maps `integer` → `BigInteger`.
- **Controller → service rule**: each controller calls exactly one service and never another one: `GeneralController` → `IBlockBetService`, `BookieController` → `IBookieService`, `BettorController` → `IBettorService`, `InternalController` → `IInternalService` (`AuthController` is left as it is). A controller method only fetches the account/params and calls `handle<Path><Method>Request(...)`; the logic lives in that service. Shared lookups for the bet services (`findBet`, `lockOwnWallet`, option mapping) go in `IBetService`/`BetService`, which only services call, never a controller. Do not set `operationId` on endpoints in the YAML: use the names the generator derives from the path and method (e.g. `blockbetBetsGet`, `bookieBetsPost`); the service method is `handle` + that name without the `blockbet` prefix + `Request`.
- **Database**: PostgreSQL `blockbetdb`, schema `dev`, localhost:5432 (postgres/postgres). Schema is managed only by Flyway migrations in `src/main/resources/db/migration` (`V0.0.x__*.sql`); add a new numbered migration rather than editing existing ones. Quartz tables are included.
- **Security**: stateless JWT (java-jwt). Custom `BlockBetAuthenticationProvider/Token/UserDetails` plus `JwtAuthenticationFilter` in `security/`; access token 15 min, refresh tokens (stored in DB, `RefreshTokenService`) 7 days. Configured under `security.jwt` in `application.yaml`.
- **Blockchain integration** (web3j): `BlockchainService` creates per-account wallets (keystore JSON files written to `IBlockBetConstant.WALLET_FOLDER_PATH`, a path relative to the repo root, git-ignored; max 10 wallets per account) and sends token transfers from a configured `blockchain.mainAccount`. Transfers are recorded as *pending* via `TransferReceiptRecorder` (with an idempotency key), and `TransferReceiptTracker` later fills in block/gas/final status once mined. Background work runs as Quartz jobs (`jobs/PendingReceiptJob`, `jobs/BetCautionJob`, with their logic classes `jobs/TransferReceiptTracker` and `jobs/BetCautionTracker`, wired in `config/QuartzConfig`, JDBC job store in the `QRTZ_` tables, clustered; intervals `blockbet.receipt-tracker.interval-ms` default 5s and `blockbet.bet-caution.interval-ms` default 60s). The tracker classes hold the logic, the jobs only call them; there is no `@Scheduled`. Addresses are stored lowercase.
- **Bets**: rules and money live in a Solidity contract per kind under `src/main/resources/contracts/` (one contract, many bets); descriptive info (title, description, image) lives in the `BETS` table. `BetContractService` encodes/sends contract calls and reads state; `BlockBetService` merges DB + chain on reads, `BookieService`/`BettorService`/`InternalService` do the writes. Each contract kind is a value of `BetContractType` (in `blockbetApi.yaml`, stored in `BET_CONTRACTS.CONTRACT_TYPE`) and lives in its own folder under `src/main/resources/contracts/` (today `simple/BlockBetSimplePool.sol` for `MULTIPLE_OPTION_SIMPLE_POOL`: one contract, 2 to 5 options per bet, options numbered 1..5 = A..E, 0 = none). Create/place/result are per-kind endpoints with the kind in the path: `POST /bookie/bets/multiple-option-simple-pool` (body `options: [...]`, 2 to 5 names), `POST /bettor/bets/multiple-option-simple-pool/{betId}/place`, `PUT /bookie/bets/multiple-option-simple-pool/{betId}/result`; they use `IBetService.findBet(betId, type)`, which answers BET_NOT_FOUND for a bet of another kind. The contract call methods in `BetContractService` do not branch on the type. To add a kind: the enum value, its `.sol`/`.bin`/`.abi` folder and an entry in `BetContractService.BIN_RESOURCES`, its own endpoints, and the contract methods in `BetContractService` if its ABI differs (`SimplePoolAbiTest` checks the simple contract's ABI against what the backend sends). `/blockbet/bets` and `/internal/bets/{betId}/refund` read/refund any kind with the simple-pool ABI (both to be redone). The backend deploys each type's `.bin` (today `contracts/simple/BlockBetSimplePool.bin`) at startup with `blockchain.mainAccount`, which becomes the contract's *internal account* (gets the pool remainder / unwon pools, logged as `BET_INTERNAL_PAYOUT` receipts, and is the only caller of `refundExpired`); the stake a bettor sends when placing a bet is logged as a `BET_STAKE` receipt (wallet → contract, no event needed: the backend sent that transaction itself, so `BettorService` builds the row from its mined receipt with `IBetService.newReceipt`); each winner's payment is logged as a `BET_PAYOUT` receipt (from the contract's `Payout(betId, to, amount, paid)` events, `paid=false` → `IS_SUCCESS` false because the amount stayed in the contract's `owed`), so one tx hash has several rows in `TRANSACTION_RECEIPTS`: it is unique on (`HASH`, `TO_ADDRESS`), not on `HASH` alone, and look a row up with `findByHashAndTransactionType`; the address is recorded in `BET_CONTRACTS` (a changed bin means a new deployment). After editing a `.sol` you must recompile and commit the new `.bin`/`.abi`: `solc --evm-version istanbul --optimize --bin --abi --overwrite -o <out> <Contract>.sol` (istanbul because `genesis.json` only enables forks up to Istanbul). `CAUTION` (bet unresolved 7 days after close) exists only in the database: `BetCautionTracker` sets `BETS.CAUTION` from the cached `BETS.CLOSE_TIME`; the contract has no such status. Endpoints: `/bookie/**` (create, resolve; role BOOKIE), `/bettor/**` (place bet), `/internal/**` (refund CAUTION bets; locked with `denyAll()` until the internal authentication process is built), `/blockbet/bets` (read; any authenticated user). Roles other than BETTOR are assigned manually in the AUTHORITIES table. Every betting action is also written to the `BETTING_LOG` table (`BettingAction`: `BET_CREATED`, `BET_PLACED`, `BET_RESOLVED`, `BET_REFUNDED`, `BET_CAUTION_FLAGGED`) through `IBettingLogService.record(...)`, which the bet services and `BetCautionTracker` call inside their own transaction; it has no foreign keys on purpose, and `ACCOUNT_ID` is null for the system and the internal team. Add a `BettingAction` and a `record` call for any new betting action. The caller reads their own rows with `GET /bettor/betting-logs?offset&limit[&betId]` (role BETTOR), declared in `bettorApi.yaml` and served by `BettorController` (`IBettorService.handleBettorBettingLogsGetRequest`).
- Errors: throw `BlockBetException` with a `BlockBetError`; `BlockBetRestExceptionHandler` converts to the REST error response.
- `application.yaml` points to the node RPC at `http://localhost:8301`, which is `node1`'s RPC (compose maps `8301:8545` on `eth-node1`; the bootnode exposes its own RPC on 8545). It also contains dev secrets (JWT key, main account private key) — dev-only values.

## Mobile architecture

Clean-architecture, feature-first under `lib/features/{auth,home,profile,receipt,splash,wallet}`, each split into `data` (datasources, models, repositories impl), `domain` (entities, repository interfaces, usecases) and `presentation` (bloc, pages). Shared code in `lib/core` (`di` with get_it, `network` with dio, `router`, `error`, `result.dart`, `usecase`, `theme`, `config/AppConfig`). State management is flutter_bloc.
